# Zig 0.16 upgrade plan for zig-evtx

## Goal

Upgrade the repository from Zig 0.15.2 to Zig 0.16 with the smallest safe change set first, then migrate the codebase from concrete `std.Io.Writer` usage to the Zig 0.16 abstract I/O model where required. Keep behavior stable for:

- CLI binary
- snapshot test tool
- unit tests and snapshot tests
- benchmarks
- optional Python extension build via pydust
- CI and cross-build workflows

This plan is intentionally implementation-ready and ordered for TDD-style execution.

## Current baseline from repository

Observed directly in the repo:

- `build.zig.zon` sets `.minimum_zig_version = "0.15.2"`.
- Local `zig version` is `0.15.2`.
- Build graph already uses 0.15-era APIs such as `createModule`, `addExecutable(.{ .root_module = ... })`, `addTest(.{ .root_module = ... })`, `addRunArtifact`, and `addLibrary`.
- The CLI and snapshot tool already use 0.15 concrete writer style:
  - `std.fs.File.stdout().writer(&buf)`
  - `std.fs.File.stderr().writer(&buf)`
  - `.interface.writeAll`, `.interface.flush`
  - file `.reader(&buf)`
- The rendering stack is strongly coupled to concrete `std.Io.Writer` pointers.
- There is a vendored `pydust.build.zig` helper that also uses current build APIs heavily.
- The package dependencies are pinned to Zig 0.15-era branches or releases:
  - `zbench` from `zig-0.15.1` branch
  - `mvzr` v0.3.7
- GitHub Actions workflows pin Zig `0.15.2`.
- Make targets shell out to `zig build ...` and assume current step names.

## Most likely Zig 0.16 breakpoints

### 1. `std.Io` migration, highest code-touch risk

Zig 0.16 introduces the new abstract I/O model and is expected to break code that assumes the 0.15 concrete `std.Io.Writer` shape. This repo has many such assumptions.

Primary symptoms to expect:

- `std.Io.Writer` type shape changes
- `.interface` field access breaks
- `File.reader(&buf)` and `File.writer(&buf)` call patterns change or need an `Io` implementation in scope
- `Writer.Allocating` usage changes
- helper functions typed as `*std.Io.Writer` stop compiling
- error aliases based on `std.Io.Writer.Error` stop compiling

### 2. process argument iteration changes in `std.process`

`src/main.zig` and `src/snapshot_tool.zig` use `std.process.argsWithAllocator`. This is a likely break candidate in 0.16 because process and stdio internals are shifting around the new I/O model.

Primary symptoms to expect:

- function rename or signature change
- allocator ownership changes
- requirement to use different arg iteration entry point
- `main()` needing to initialize `std.Io.Threaded` and pass `io` down before any argument or stdio work

### 3. build system API drift

The repo already uses relatively new build APIs, which lowers risk, but Zig 0.16 often changes details rather than the top-level pattern.

Primary symptoms to expect:

- `standardTargetOptionsQueryOnly` and target plumbing drift
- `createModule` field changes
- `addLibrary` or install-step signature changes
- `addRunArtifact` step options or stdio options changes
- `linker_allow_shlib_undefined` relocation or rename
- `TranslateC` step API changes
- `addOptions().createModule()` behavior changes
- install path helpers changing in pydust integration

### 4. dependency compatibility

`zbench` is pinned to a branch named `zig-0.15.1`. That is a direct warning sign.

Primary symptoms to expect:

- fetch succeeds but compile fails in benchmark targets
- benchmark API drift even if library compiles
- transitive stdlib assumptions in dependencies

`mvzr` may also require a newer tag or patch, even if its surface area is smaller.

### 5. CI and packaging drift

Even if native `zig build test` passes, CI and packaging can still fail because workflows and Make targets pin old versions and Python build glue may lag.

## Concrete I/O migration map

This is the part most likely to dominate the upgrade.

### Current concrete writer coupling

The following files explicitly type APIs as `*std.Io.Writer` and should be treated as one migration cluster:

- `src/parser/err.zig`
- `src/parser/value_format.zig`
- `src/parser/render_xml.zig`
- `src/parser/render_json.zig`
- `src/parser/util_string.zig`
- `src/parser/util_simd.zig`
- `src/parser/evtx/output.zig`
- `src/evtx_pydust_impl.zig`
- `src/bench_utf_zbench.zig`

The following files explicitly depend on 0.15 `.interface` or `reader(&buf)` / `writer(&buf)` values and should be migrated alongside entrypoint setup:

- `src/main.zig`
- `src/snapshot_tool.zig`
- `src/bench_serialize.zig`
- `src/bench_utf_zbench.zig`
- `src/evtx_pydust_impl.zig`
- `src/parser/evtx/format.zig`
- `src/parser/evtx/worker.zig`
- `src/test/snapshot_tests.zig`

### Recommended abstract-I/O target shape

Use one 0.16-compatible pattern consistently:

1. Initialize the I/O implementation near program entry, likely in each executable `main`.
2. Pass `io` or abstract reader/writer handles downward rather than concrete `std.Io.Writer` pointers.
3. Keep parser logic generic over the minimum capability required.
4. Keep serialization APIs abstract at the boundary and concrete only inside scratch-buffer helpers when unavoidable.

### Migration strategy for repository code

1. Start at the leaves.
   - Migrate `err.zig`, `value_format.zig`, `util_string.zig`, `util_simd.zig`, `render_xml.zig`, `render_json.zig` first.
   - Replace direct dependency on `*std.Io.Writer` with the narrowest 0.16-compatible writer abstraction.

2. Migrate `OutputWriter` next.
   - This file is the choke point for XML and JSON serialization.
   - Decide whether `scratch` remains an allocating writer, or becomes an `ArrayList(u8)` plus abstract writer adapter.
   - Avoid spreading 0.16-specific writer construction across the whole codebase.

3. Migrate entrypoints after the writer stack compiles.
   - `main.zig`
   - `snapshot_tool.zig`
   - benchmarks
   - pydust implementation helpers

4. Migrate reader construction after entrypoint I/O initialization is understood.
   - `format.zig` is the main reader abstraction seam.
   - remove the 0.15-specific `.interface.readSliceAll` detection path and replace it with 0.16-compatible abstract reads

## Dependency and ecosystem risks

### `zbench`

Current dependency:

- `build.zig.zon`: `https://github.com/hendriknielaender/zBench/archive/refs/heads/zig-0.15.1.tar.gz`

Risk:

- very likely incompatible with 0.16

Plan:

- first check whether upstream has a Zig 0.16 branch, tag, or mainline support
- if yes, update URL and hash in `build.zig.zon`
- if no, temporarily gate benchmarks behind a feature flag or defer benchmark target restoration until main build and tests are green

Recommendation:

- do not let benchmark dependency block the core parser upgrade

### `mvzr`

Current dependency:

- `mvzr` v0.3.7

Risk:

- lower than `zbench`, but still needs validation against 0.16

Plan:

- check upstream release notes or tags for 0.16 support
- update in `build.zig.zon` only after confirming compatibility
- if breakage is small and local, consider a temporary repo patch after the main upgrade lands

### `pydust`

Current state:

- custom vendored helper in `pydust.build.zig`
- Python build flow depends on `ziggy-pydust==0.26.0` installed by `makefiles/python.mk`

Risk:

- high for build-script API breakage
- medium for runtime parser code because pydust-facing parser code is relatively isolated

Plan:

- verify whether `ziggy-pydust` version used here supports Zig 0.16
- if upstream ships a 0.16-compatible helper, prefer syncing from upstream over hand-editing the vendored helper blindly
- if upstream is not ready, split the upgrade into:
  - core Zig CLI/test upgrade first
  - Python extension upgrade second

Recommendation:

- treat Python extension support as a separate acceptance gate after `zig build test` and `zig build snapshot` are green

## Test sequence to use during the upgrade

Run these in order after each task cluster. Keep failures narrow.

### Baseline before any code change

1. `zig build test`
2. `zig build snapshot`
3. `make test`
4. `make snapshot`
5. `zig build run -- -t 1 -o xml samples/system.evtx`
6. `zig build run -- -t 1 -o jsonl samples/security.evtx`

Record any existing failures before touching the compiler version.

### After build-system and dependency changes, before code migration

1. `zig build test`
2. `zig build snapshot`
3. `zig build bench-zbench` only if `zbench` was updated and expected to work
4. `zig build bench-serialize`

### After abstract writer migration

1. `zig build test`
2. `zig build snapshot`
3. `./zig-out/bin/snapshot_test`
4. `./zig-out/bin/evtx_dump_zig -t 1 -o xml samples/system.evtx | head -n 5`
5. `./zig-out/bin/evtx_dump_zig -t 1 -o json samples/security.evtx | head -n 5`

### After reader and entrypoint migration

1. `make build`
2. `make test`
3. `make snapshot`
4. `make build-all TARGETS="x86_64-linux aarch64-linux"`

### After Python path is restored

1. `make py-editable`
2. `make py-test`
3. `make py-wheel`
4. `make py-wheel-dump FILE=samples/system.evtx FORMAT=xml`

### Final pre-merge sequence

1. `zig fmt src/**/*.zig build.zig pydust.build.zig`
2. `zig build test -Doptimize=Debug`
3. `zig build snapshot -Doptimize=Debug`
4. `zig build -Doptimize=ReleaseFast`
5. `make test`
6. `make snapshot`
7. native smoke parse on at least one XML and one JSON sample
8. Python extension tests if that feature remains supported

## TDD and review mindset for execution

Use this review loop for every task:

1. Make one narrow change.
2. Run the smallest command that exercises it.
3. Fix the next compile error in dependency order.
4. Only move outward after leaf utilities are green.
5. For rendering changes, compare output bytes and snapshots before refactoring more.

Specific discipline for this repo:

- do not refactor parser logic while upgrading I/O APIs
- preserve CLI behavior and output format byte-for-byte where possible
- keep concurrent parser behavior unchanged until after sequential path is green
- prefer adapter layers over broad rewrites
- gate optional pieces temporarily if they block the parser core

## Suggested first implementation pass

When actual coding starts, the highest-probability path is:

1. update `build.zig.zon` and dependency pins
2. get `build.zig` compiling on 0.16
3. port `parser/err.zig`, `value_format.zig`, `util_string.zig`, `util_simd.zig`
4. port `render_xml.zig`, `render_json.zig`

7. port `format.zig` reader helper
8. run tests and snapshots

## Acceptance criteria for the upgrade

The Zig 0.16 upgrade is complete when all are true:

- `build.zig.zon` minimum version is Zig 0.16
- `zig build test` passes on Zig 0.16
- `zig build snapshot` passes on Zig 0.16
- CLI smoke tests parse sample EVTX files in XML and JSON modes
- snapshot outputs remain stable or changes are explained and reviewed
- Make targets still work for build, test, snapshot, and selected benchmarks
- benchmark targets either pass on updated dependencies or are intentionally gated with documentation
- Python extension build and tests pass, or temporary support status is documented in repo docs and CI
- GitHub Actions workflows target Zig 0.16

## Known likely blockers to resolve early

- `zbench` 0.15 branch incompatibility
- `pydust.build.zig` divergence from upstream Zig 0.16 support
- `std.process.argsWithAllocator` churn
- `std.Io.Writer.Allocating` replacement details
- `.interface` removal across file/stdout/stderr writers and readers

## Recommended decision points

### If `zbench` is not Zig 0.16 ready

Proceed with core upgrade and leave benchmark restoration to a follow-up commit.

### If `pydust` is not Zig 0.16 ready

Proceed with core CLI/test upgrade first. Mark Python extension support as a temporary follow-up. Do not hold parser migration hostage to external packaging glue.

### If abstract `std.Io` requires broad entrypoint changes

Create a small local compatibility layer for stdout, stderr, file readers, and allocating output. Keep the rest of the parser code insulated behind that layer.

## Final recommendation

Execute the upgrade in two tracks:

- Track A, required for success: core build graph, parser, renderers, CLI, snapshot tests, CI pinning
- Track B, optional recovery after Track A is green: benchmarks and Python extension

That order minimizes external dependency drag and keeps the main parser upgrade reviewable.
